# PersonaOS D3：设备类型配置发布、回滚与设备实例继承

## 核心不变量

D2 能力草稿**不是**在线配置。D3 必须明确区分以下四层：

1. **资源目录与 Character**：可编辑、可复用的管理资源；修改资源不应默默改变历史发布内容。
2. **设备类型草稿**：以 DeviceType ID 为聚合入口，管理员可反复修改，必须满足引用存在、类型及启停校验。
3. **已发布配置版本**：某个 DeviceType 的不可变全量快照，包含角色人格、设备型号硬件属性、Voice、Tool、Skill、知识库的已解析元数据。发布后不能修改快照；更新目录或草稿不影响它。
4. **设备实例**：物理设备唯一标识，绑定一个设备类型，默认继承该类型当前已激活的发布版本；如业务需要，后续允许显式锁定某个已发布版本。实例永远不能直接继承草稿。

**硬件能力、配置中关联的 Tool、Runtime 真正支持的 Tool、鉴权/安全策略是独立条件**。即使 A4 具有摄像头，也不会仅凭这个字段获得视觉工具运行权限。

## 分阶段实施

- **D3-1：发布领域契约（本 PR）**：`PublishSnapshotInput` 传入已解析候选，`NewPublishedDeviceConfig` 校验设备/角色关联、版本、发布人、时间及完整且已启用的四类能力资源。返回完整快照及 Clone 防御性拷贝。只新增领域代码和单测，**不新增 HTTP 路由、表、菜单或上线行为**。
- **D3-2：MySQL 发布与激活事务**：同事务锁定 DeviceType、读取草稿及资源和角色，在事务里构建快照；每种设备类型独立单调递增版本号；保存 JSON/规范化版本记录，并原子切换活动版本指针。并发发布串行化，数据库错误整体回滚；对未发布的型号不返回有效运行配置。
- **D3-3：发布、版本历史与回滚 API**：受管 API 使用专门的 `publish/activate/read` 权限、操作审计及最小授权；激活已有历史版本时只改变当前活动指针，**历史版本仍不可变**。发布操作返回被激活的版本 ID 与快照（需要明确并发、幂等与重复发布语义）。
- **D3-4：设备实例继承**：设备实例唯一 ID 与 DeviceType 绑定。默认浮动继承当前活动版本；可选固定版本模式必须显式配置、审计。只能读取已发布内容；失效、未发布或不存在时不得回退到草稿。
- **D3-5：后台与完整验收**：发布前查看差异、确认、历史版本、激活/回滚操作、实例当前有效版本；真实 MySQL 多角色权限、并发发布、失败回滚、浏览器 E2E。Agent Runtime 实际加载和执行仍需后续独立的能力鉴权与设备硬件校验。

## 安全与存储边界

- 快照仅包含标识及非敏感元数据；不保存音色厂商密钥、API Token、密码、可执行脚本等。
- 快照构建时验证所有引用正数、不重复、类型正确、当前启用、与 Device Type 的草稿完全一致；引用数量不匹配时拒绝发布，**不能静默丢弃无效资源**。
- 对所有已发布快照返回 Clone，杜绝输入或读取端对数组及可选 Voice 指针的别名修改。
- 版本号必须由数据库事务分配，不能由前端提供；D3-1 接口中的 `Version` 只是给后续事务层传入，领域层仅验证为正数。
- 回滚是活动指针切换（写审计记录），不是删除或重写历史版本；无活动版本时设备无生效配置。
- A3/A4 共享 Character 时各自有独立版本序列与活动指针，角色更新后只有重新发布的型号才会包含新人格快照。
