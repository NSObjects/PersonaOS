# PersonaOS Demo：设备类型配置生效

当前目标是**快速演示角色 AI 玩具的完整语音 Agent 交互**，不是建设多版本发布平台。任何设备型号均在后台创建，不在代码中固定 A3、A4 等名称。

## 配置关系

- Character 是可复用角色人格。
- Device Type 是由后台创建的产品型号，关联 Character，并独立配置音色、Tools、Skills 和知识库。实际设备拥有的摄像头等硬件能力不等于 Tool 执行授权。
- 草稿可以反复编辑，但**不直接影响已生效的配置**。
- 管理员点击「应用配置」时，服务端在 MySQL 事务中读取该设备类型、角色、资源关联，验证所有资源并保存**唯一的当前生效快照**。
- Agent Demo 只能读取确认生效的快照；没有确认的设备类型读取返回 404。每次应用递增技术修订序号，但不保存历史记录、回滚入口或复杂审批流程。
- 一个型号的配置变更不得影响另一个型号，即便二者共享角色。

## 后台操作

1. 创建角色。
2. 创建任意名称的设备类型并关联角色。
3. 在「能力资源」中创建所需音色、Tool、Skill 与知识库引用。
4. 打开设备类型的「能力草稿」，选择能力并保存。
5. 点击该设备类型的「应用配置」，确认后可点击「生效配置」查看被固定的角色、音色和能力清单。

管理 API：

- `GET /api/device-types/:id/active-config`：读取已生效快照，受 `device_type:read` 管理权限保护。
- `PUT /api/device-types/:id/active-config`：应用当前草稿，受 `device_type:update` 管理权限及操作审计保护。

这两个端点是后台管理接口，不作为未经认证的硬件公共接口。实体设备的身份验证与实例绑定仍需要在真实设备接入时实现。

对于已初始化的数据库，先备份，再执行 `go run . upgrade-access-authorization --config configs/config.toml` 同步新受管 API 的授权记录。

## 接下来的最短路径

1. **已做：** 后台配置和唯一生效快照。
2. **下一步：** 基于同一生效快照实现最小 Go Agent 对话：角色人格 + LLM；按配置约束可用 Tool，禁止未经授权的调用。
3. **随后：** 对接现有 ASR/TTS SDK 和设备音频协议，展示语音对话及可用的动作/表情。
4. **最后：** 录制完整 Demo：后台改配置、设备重新加载、角色对话和能力差异演示。

当前不做多版本、回滚、复杂设备管理、支付、报表或额外 Agent 工作流；这些不应阻塞 Demo。
